✦ WHY IT MATTERED

A design system only counts where users see it.

Users never see the design file. They see the product, and the product is code. As long as design lives in one place and code in another, every decision has to be translated by hand on its way to the product.

At snelstart, even a small visual change to an existing component was front-end work. That takes developer time for something that isn't really a development question, and it keeps designers one step away from the product they design.

So I approached the design system review from the code side. Not a tidier Figma library, but a system that design and front-end both build on.

✦ KEY DECISIONS

The calls that shaped it.

Decision 01

Tokens before components

A colour or a spacing value should be one change in one place, not a search through screens. Getting the structure right first is what makes every later step safe to automate.

Decision 02

A repository, not a file

A repository gives tokens version history, review and one place that design and front-end both trust. It doesn't belong to one app or one tool.

Decision 03

A pipeline, not a hand-off

Once a pipeline publishes the tokens, a design decision doesn't need a developer to retype it before it reaches the product.

Decision 04

New components stay with front-end, for now

A new component carries behaviour, planning and a question of who owns what. That isn't ours to take yet. Changing what exists is a different job from deciding what should exist, so I kept the scope to the first.

✦ HOW IT CONNECTS

The same idea as the AI flow, one layer down.

In the Ask-a-designer flow, product owners get a designer to ask, and a designer approves what ships. Here, designers get a direct line into the code, and the front-end team keeps what is theirs. In both cases the work is deciding who owns which decision, and making the hand-over cheap.
